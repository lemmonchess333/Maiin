# Recorded activity linkage, inactive stage

reconcileRunningActivityTransaction accepts only expectedUid, expectedRevision and activityId. The activity identity is its durable idempotency key. Retries must retain the original expected revision. The server derives its launch and activity receipt paths; the client supplies no clinical assessment, completion verdict, session target or evidence facts.

The transaction checks authenticated account, profile, deletion ledger/tombstone, rollout protocol and completionEnabled, current authority revision/migration, immutable server-authorized app-start proof, and the actual saved run in that account's runs collection. It requires exact saved canonicalLaunch provenance, both legacyPlanClaimExcluded markers, valid explicit recordingStartedAt within the original 15-second start window, recordingEndedAt no later than server now, and compatible reported duration. Earlier preparation startedAt is not sufficient. Missing/foreign/invalid activity, receipt-only or canceled start with no saved activity, edited identity, changed canonical session and incompatible data cannot link.

The result is classified user_reported_activity with progressionEligible:false. Neither route/duration nor an app-start receipt proves exercise, interval execution, medical readiness or completed_exact. Partial recordings can be linked as recorded activity, never stage progression. Existing injury/pause/recovery holds are preserved even when they were added after the start.

An atomic activity receipt and authority.recordedActivityLinks[sessionId] link are written; the latter is visible in authenticated negotiation. Plan rows, accepted stage, constraints, goal, raw saved activity and history remain unchanged. The renderer must label the session 'Activity recorded', not completed, and suppress its Start action. Server launch independently rejects any own session link. Linkage advances revision, deliberately staling the review marker: remaining sessions need an explicit fresh review before launch. No automatic renewal or independent hold clearance occurs.

Receipts live under runningState/activity_<SHA256([uid,activityId])>, already within owner-read/Admin-write rules and recursive account deletion. Exact replay checks the original evidence fingerprint, stored link and receipt, never writing a second revision. Saved-activity edits require a future explicit correction workflow; this command does not silently rewrite accepted evidence.

Focused testing exercises real enrollment/review/migration/adoption/register/save/link/negotiation and the next-session review boundary. Separate local-emulator tests cover concurrent linkage and missing saved activity; they remain skipped without an emulator host. Memory-store results are not concurrency proof. No deployment, publication, live-account access or feature activation is part of this stage. Callable/client invocation remains default-off and is integrated separately.
