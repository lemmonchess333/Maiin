# Explicit recorded-activity linkage (inactive candidate)

RunSummary offers “Record against this session” only after ordinary save and only when both source-only running flags are enabled. Both flags remain false. Saving, queueing, opening the receipt, sharing, and leaving the screen never invoke linkage automatically.

The explicit action first reads the saved run from the server, rejecting missing, cached, or pending snapshots. It reads transaction authority to choose an initial expected revision, then persists only account/activity/revision as the retry identity before calling the authenticated command. The backend remains authoritative for immutable start receipts, exact saved provenance, and user-reported classification. A matching receipt is required before showing success. Neither receipt nor UI asserts exact interval execution, medical readiness, stage completion, or progression credit. Existing holds remain; linkage advances authority revision and a later planned start needs a fresh explicit review.

A same-origin browser Web Lock serializes request creation and submission across tabs/remounts. Unsupported clients fail closed. Storage read failure is distinct from absence; malformed or unreadable retry requests are not replaced. Lost responses retry the same persisted revision. Only a known revision-conflict rejection offers a separate reset action, and guarded reset checks the exact rejected revision under the same lock so it cannot delete another tab’s newer request. Reset never submits: a further explicit click is needed. Account-session identity and connection are rechecked around asynchronous work.

Focused tests cover server persistence, cache/pending rejection, source identity, lost response, concurrent calls, storage read/write failure, malformed receipts, stale reset, account changes while waiting, offline state, duplicate clicks, unmount, conservative copy in light/dark class contexts, and reset recovery. DOM theme tests are not screenshot or contrast QA. No live account, browser end-to-end session, emulator socket, rollout activation, upload, publication, or deployment is part of this validation.

Remaining operational constraints: only the current saved-run summary carries this explicit action; no background replay, universal cross-device request recovery, or old-client enforcement is claimed. Local retry metadata has no health answers and remains scoped per account/activity. Clearing device data after an uncertain outcome may require recovery beyond this UI. Full aggregate results belong to the integration report for the exact final commit.
