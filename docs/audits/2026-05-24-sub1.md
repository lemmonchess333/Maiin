# Sub1 audit — 2026-05-24

**Scope:** Sub1 (Stripe / Apple IAP subscription flow) locked
decision vs. current implementation. Lock row lives in
`.claude/plans/programme-run-followups.md` (line 534).

## Headline

Sub1 has the biggest implementation drift of the three recent
locks. Two critical issues:

1. **Zombie-charge risk on account deletion** — R1A pin (b) not
   implemented. A deleted Pro user keeps getting billed indefinitely.
2. **Trial structure is fundamentally different** — Sub1a's
   "explicit opt-in + payment upfront + auto-converts" model was
   never built; current implementation is "free 7-day grant at
   signup, no payment captured, no conversion mechanism".

Neither is user-visible pre-launch (zero Pro subscribers, no real
trial-conversion attempts), but both block real subscription launch.

## Findings

### 1. R1A pin (b) — zombie-charge risk on account deletion (severe)

**Lock:** "Active subscription at deletion: deletion executor MUST
call `subscription.cancel()` via Stripe API + send Apple IAP
cancellation request via App Store Server API BEFORE purging user
data — prevents zombie charges on deleted account".

**Current:** `functions/accountDeletion.js` (213 lines) executes the
deletion sequence: user subcollections → top-level user-keyed
collections → activities → user-doc → Auth user. **Zero references
to `stripe`, `subscription.cancel`, `appleIAP`, or
`appleOriginalTransactionId` in the executor.** The user's
`stripeCustomerId` / `appleOriginalTransactionId` fields are simply
deleted along with the user doc; no API call is made to either
provider to actually cancel the subscription.

**Consequence:** A Pro user who deletes their Tropos account today:

- Their user doc is removed, so Tropos forgets they're Pro.
- Their Stripe subscription continues to bill the card on file every
  month (or year) indefinitely.
- The Stripe webhook handler does catch the resulting events and
  routes them to `paymentEventsPostDeletion` (R1A pin c works) — but
  the charge has already happened. The webhook can't refund.

**Pre-launch this is academic** (no Pro subscribers exist). It
becomes a real billable bug the moment the first Pro user deletes
their account post-launch.

**Fix shape:** Add a step to `deleteAccount` BEFORE the user-doc
delete that reads `stripeCustomerId` / `stripeSubscriptionId` /
`appleOriginalTransactionId` from the user doc, calls
`stripe.subscriptions.cancel(subscriptionId)`, calls Apple's
App Store Server API cancellation endpoint, and absorbs errors
(don't block deletion if the provider call fails — log to
`subscriptionCancellationFailures` for operator follow-up). Add the
collection to `accountDeletionInventory.json` so the drift test
catches a future regression.

### 2. Sub1a trial structure — fundamentally different (high impact at launch)

**Lock:** Trial starts only on explicit "Start Pro trial" tap from
ProModal/Upgrade page; payment method captured at start (Stripe card
upfront + Apple IAP confirm sheet); converts to paid automatically
at day 7; `hasUsedTrial` flag prevents trial-shopping (per-UID, with
IP-rate-limit mitigation for the new-account-shopping vector).

**Current implementation:**

- `createDefaultProfile()` (`src/lib/auth.tsx:309`) sets
  `trialExpiresAt: getTrialExpiresAt()` (7 days from now) for
  **every new account** — no opt-in.
- `getTrialExpiresAt()` (`src/lib/auth.tsx:261`) just does `new
Date().setDate(+7)`. Trial length is correct (7 days); trigger is
  wrong (signup, not opt-in).
- No `hasUsedTrial` field exists anywhere in the codebase (grep
  confirms: zero hits in `src/`, `functions/`).
- No payment method captured at trial start. New users get 7 days
  of Pro features for free, no card, no commitment.
- `functions/index.js:1317` `createCheckoutSession` builds a Stripe
  session without `subscription_data.trial_period_days` — when the
  user does check out (after their free 7 days expire), they pay
  immediately; no Stripe-side trial discount.
- No auto-conversion path. At day 7, `isPro` flips to `false`; the
  user stays free until they explicitly check out. The locked design
  has the trial convert to paid automatically.

**Pin scorecard:**

- Sub1a pin #1 (`hasUsedTrial` flag, IP-rate-limit mitigation) →
  0% implemented.
- Sub1a pin #2 (payment captured at trial start) → 0% implemented.
- Sub1a pin #3 (trial starts only on explicit opt-in) → 0%
  implemented (the inverse: trial starts on account creation).
- Sub1a pin #4 (cancellation pre-conversion = no charge) → moot
  today (no charge to begin with).

**Pre-launch this is harmless** — there's no payment plumbing being
abused. Post-launch, two failure modes appear:

- **Trial-shopping:** Users can register a new email, get 7 days
  free, churn, repeat. No `hasUsedTrial` flag to stop them.
- **Zero conversion funnel:** "Free trial that auto-converts to
  paid" is the standard subscription-funnel template. Tropos's
  current trial is a free demo with no funnel — users opt INTO paid
  affirmatively after their free-trial ends, which is a much higher
  friction than the locked design.

**Fix shape:** Move trial grant from `createDefaultProfile()` to an
explicit "Start Pro trial" handler in ProModal / Upgrade. Add
`hasUsedTrial: boolean` to `UserProfile` (default `false`); check +
set on the explicit-tap handler. Add `trial_period_days: 7` to the
`stripe.checkout.sessions.create` call when starting a trial. Wire
the trial-end Stripe webhook event to the existing
`stripeWebhook.subscription.updated` handler (verify it correctly
sets `isPro = true` post-conversion). Add a trial-end notification
schedule per the lock's critical-implications #12 (Day 5 email, Day
6 in-app banner, Day 7 conversion).

### 3. Sub1b reconciliation guards (pins #1-3) — routing OK, guards missing

**Routing:** `src/lib/purchaseProvider.ts:62` `isNativeIOS()`
correctly forks: iOS → Apple IAP path, web/Android → Stripe.
`useProCheckout.ts:103` calls `isNativeIOS() ? "ios" : "web"` and
the `purchase()` function routes accordingly. ✓

**Pin #1 (web Upgrade page detects existing IAP Pro):** Not
verified in this audit. Need to check whether
`src/pages/Upgrade.tsx` consults `subscription.tier === 'pro'`
before showing checkout. If a user upgraded via IAP on iOS then
opens the web app, the locked design surfaces "You're already a Pro
member via the App Store — manage on iOS" instead of showing a
duplicate checkout. Current behaviour unverified.

**Pin #2 (cross-platform duplicate-subscription detection + admin
alert):** Not implemented as a bundled flow. Stripe webhook
(`functions/index.js:1490` `customer.subscription.updated`) and
Apple webhook (`functions/appleIAP.js:208` `appleIAPWebhook`) both
handle individual platform events but neither cross-checks whether
the same UID has an active subscription on the OTHER platform. A
user who somehow ends up with both an active Stripe sub and an
active Apple IAP sub would not trigger any reconciliation or admin
alert. (Low-risk pre-launch; closes the door on rare cross-platform
upgrade edge cases.)

**Pin #3 (`subscription.source` field):** Not implemented. User docs
have provider-specific fields (`stripeCustomerId`,
`appleOriginalTransactionId`) but no unified `source: 'stripe' |
'ios_iap' | 'android_iap'` discriminator. Lookups have to test for
the presence of either field instead of reading a single
authoritative source.

### 4. Sub1c grace periods — Apple aligned by default; Stripe unverified

**Apple's 16-day grace:** Happens automatically via Apple's
server-side retry logic. The Apple webhook receives the eventual
expired/renewed event. Tropos doesn't need to do anything special —
the lock explicitly defers to Apple. ✓

**Stripe's 3-day grace via dunning:** Requires (a) Stripe Customer-
level dunning configuration (Settings → Subscriptions → Dunning),
(b) Tropos-side grace-state tracking (so the UI can render
"Subscription paused, update your card" banner), (c) the Day-0 /
Day-1-2 / Day-3 email + banner cadence per critical-implications
#7. None verified — pre-launch this is not testable end-to-end
(real card-failure events don't fire on a test account without
Stripe's CLI replay tools). Defer verification to first real
post-launch failure event.

### 5. Sub1d cancel-at-period-end — aligned in spirit

Cancellation in Tropos delegates to:

- Stripe Customer Portal (web users) — `manageSubscription(uid)`
  from `purchaseProvider.ts` returns a redirect URL to the portal,
  where the user can cancel.
- App Store subscription settings (iOS users) — per Apple's UI
  mandate.

Both Stripe and Apple natively support cancel-at-period-end
(Stripe's customer portal default cancellation flow; Apple's
"Cancel Subscription" in App Store settings). ✓

**Pin #1 (cancel requires fresh `auth_time` per A1c-D):** Stripe
Customer Portal handles its own auth (separate login state); Apple
handles its own (App Store password). Tropos's A1c-D re-auth gate
applies to in-app destructive actions; cancellation happens
out-of-app via the providers. Compliant by delegation.

- **Track P2 (pre-launch hardening, ~1 day):** Sub1b reconciliation

- **Track P3 (post-launch verify):** Sub1c Stripe dunning end-to-end

## Decision point

Sub1's lock specifies a more sophisticated subscription model than
what's shipped. The session must choose:

- **(a) Implement to the lock pre-launch** — Tracks P0+P1+P2 = ~3
  days of focused work before first Pro subscriber.
- **(b) Revise the lock** to match what's actually buildable in the
  pre-launch window — would need a `/grill-me` re-pass on Sub1a's
  trial mechanics; risk = re-deciding without the empirical signal
  the lock was originally calibrated against.
- **(c) Launch with the simpler current model and revisit
  post-data** — acceptable IF the current "7-day free demo, then
  affirmative checkout" funnel is honestly communicated to users
  ("Try Pro free for 7 days" is fine; "Free 7-day trial that
  converts to paid" is not, because that conversion doesn't
  happen).

Track P0 (zombie-charge fix) is non-negotiable regardless of which
of (a)/(b)/(c) is chosen — once one user is paying, deletion must
cancel the subscription.
