# Connected training: Apple Watch runs and Apple Health

**Status:** Implementation in progress, 31 October 2026. The Watch target, phone bridge, and Health export path are behind disabled release gates. Server receipts cover reinstall duplicate prevention and cross-device deletion cleanup in code. The PR macOS simulator build passed; signing, paired-device controls, and HealthKit behavior still need verification before release.

## Decision

Build a phone-led Apple Watch companion for outdoor runs first. The iPhone remains the only run recorder and the only writer of a Tropos run. The Watch shows the active run, supplies heart rate, and can pause, resume, or end recording only when the iPhone acknowledges the command. Finishing on the Watch opens the existing review and save path on the iPhone. A Watch action alone never completes a planned session.

Keep phone-free Watch recording and lifting set entry as later releases. Both require more than a Watch screen: independent session storage, precise reconciliation with the plan, and safe recovery after disconnection. This sequence gives runners a useful wrist experience while preserving Tropos's existing run, route privacy, and completion rules.

The companion is part of free training. Do not add a paywall or another mandatory onboarding step.

## Evidence and current boundary

- Mobbin's [Runna Apple Watch connection](https://mobbin.com/flows/fc01ea0c-344b-4ec0-b2c1-767d4d7ca5c6) spans six captured iOS screens. It shows device permissions, planned workouts on the Watch, and completed workouts syncing back. [Runna Watch settings](https://mobbin.com/flows/5df3081f-e3ce-4dcc-a986-7342b6ccf52c) expose mirroring and sync controls. [Hevy Home](https://mobbin.com/flows/cb35f86e-f8e5-4511-b73a-556084d226a8) offers an Apple Watch connection for workout logging. These are interface references, not evidence of conversion or retention gains.
- At the decision point, Tropos read Apple Health steps through `src/lib/healthKit.ts`; the iOS live heart-rate source was unavailable and `ios/App/App.xcodeproj` had no watchOS target. The implementation on this branch adds those paths behind release gates.
- The current iPhone run engine owns GPS, timing, pause state, route privacy, the summary, and the save. `src/pages/Run.tsx` runs the session; `src/pages/RunSummary.tsx` reviews and clips the route; `src/lib/runCompletion.ts` makes a durable create-only save. The first release must use those boundaries.
- The accepted `docs/adr/0007-healthkit-reconciliation.md` makes Tropos sessions authoritative. Apple Health workouts are never silently imported into plans, streaks, challenges, or performance calculations. Workout write-back is opt-in. Apple Health energy never changes calorie targets or the adaptive nutrition model.

## Product goal

An athlete can start a planned outdoor run on the iPhone, see useful live information on the Watch, control a connected run from the wrist, and finish with exactly one saved Tropos run. Heart rate appears when the Watch supplies it. The run remains fully usable on the phone without a Watch or heart rate permission.

The first release is successful when paired-device tests show reliable run state and command acknowledgements with the phone locked, one canonical save, correct plan credit, and no route or health-data leak across accounts. Usage and retention effects remain questions for post-release measurement.

### Connection states

The Settings row and Watch app distinguish **Not available here**, **Watch app not installed**, **Ready**, **Connecting**, **Active run**, and **Connection lost**. A read permission that Apple does not disclose is reported as **No heart rate yet**, with an Apple Health settings recovery path, rather than a false **Denied** state. A signed-out iPhone clears the Watch's account and plan context. A newly signed-in account cannot inherit the previous account's session.

## One-authority session contract

1. Generate and persist a stable `sessionId` at run start, bound to the current `uid`, the selected plan session if any, and the original start instant, local date, and time zone. Map it to the final run document ID before recording, including in the recoverable run snapshot and offline receipt. The current snapshot has no ID and `completeRun` allocates one at Save, so this is new work that closes a duplicate-save crash window. Capture the first actual timer start and the recording end separately from the Start tap and later Save time. Keep active `duration` separate from the wall-clock span so GPS waiting and pauses do not lengthen the Apple Health workout. `runDocument` currently writes `completedAt` from save time and derives `date` in the phone's time zone at save; write the canonical `date` from the captured start-local date and add explicit recording-start, recording-end, and origin-zone fields without silently changing legacy `completedAt` consumers. Update historical run read windows, currently keyed on `completedAt`, so a late save remains discoverable on its original day. The Watch never writes Firestore or changes a plan directly.
2. Each Watch command contains `sessionId`, a unique `commandId`, an expected session revision, and one action. The phone applies an action at most once, only to the active session and account, then returns the authoritative state and revision. A timeout is not an acknowledgement. The Watch must display the returned state rather than an optimistic local transition.
3. On Finish, the phone enters its current summary and review path. `completeRun` retains one document identity across retries after the new start-time ID is threaded through it. Only a valid saved run can claim an eligible scheduled run, and one saved run can claim at most one planned day. The existing claim map can match a free run by date, distance, and quality, including a run on the day after a planned session; the Watch creates no additional claim or stricter rule. A Watch finish, a HealthKit workout, and an offline queue entry are not independent plan evidence.
4. Watch heart rate samples carry source, sample time, and a sequence identity. A bounded, protected local buffer survives app death and delayed phone review, and deduplicates retransmission. Raw samples are used for the live display and a session summary, then discarded after the canonical save or discard; do not put raw heart rate in analytics. Save average, maximum, zone durations, covered duration, source, and the max-heart-rate setting used for calculation only when there is valid coverage.
5. Zone duration must use sample timestamps and exclude long missing intervals. The existing `zoneDistribution` counts samples equally, so it must not be labelled **time in zone** without a time-weighted implementation. When fewer than half the run's moving seconds have heart rate coverage, hide the zone chart and explain that the reading was partial. Never infer missing heart rate or change the run's calorie, training load, nutrition, or readiness calculations in this release.
6. Apple Health workout write-back is a separate opt-in. With it off, Watch heart rate collection must leave no saved Apple Health workout. After the server confirms the canonical Tropos save, write exactly one `HKWorkout` using the run's actual start/end, distance, and app-owned energy estimate. A watchOS workout session used to capture heart rate may itself create an Apple Health workout: the prototype must prove whether that sample can be discarded or whether write-back must reuse/link it, so Tropos never double-counts a run in Health. Use a stable Tropos run identity in HealthKit metadata or an equivalent idempotent mapping so retries and reinstall do not export duplicates. HealthKit workouts are immutable: correcting one means deleting the app-owned sample and writing a replacement. If write access is revoked, keep a durable pending-reconciliation state and show it in Settings; do not write a replacement until the old sample can be removed. Do not export the GPS route in this release. Imported third-party workouts remain outside plan, streak, challenge, and performance credit under ADR-0007.
7. A durable local queue receipt means **Saved on iPhone · syncing**, not server confirmation. Show **Synced to Tropos** only after the canonical server write is confirmed. If privacy zones have not been confirmed by the server during the current app session, the existing route save is blocked while offline; the Watch must not claim that such a run was saved. Keep the route private and offer the existing retry path when connectivity returns.

The Watch-to-phone bridge must not carry the full route or nutrition profile. Clear session context and pending samples on account change or discard. Keep the raw GPS route in the existing phone privacy flow. Do not add health values, locations, or session IDs to product analytics.

## Native feasibility gate

Before building the full UI, prove the following on a paired iPhone and Watch with the phone locked and the run active:

1. A watchOS workout session can collect heart rate and make it available to the iPhone at a useful cadence, including after a brief disconnect. Do not assume an iPhone HealthKit query receives live Watch samples.
2. The native bridge can deliver a Watch Pause, Resume, and End intent to the phone and return a durable acknowledgement while iOS backgrounds the app. Background GPS surviving a lock does not prove React's current `Run.tsx` handlers can process Watch commands while suspended. If those handlers cannot run reliably, add a native session coordinator that owns and reconciles those transitions before promising wrist controls.
3. A Watch Finish received with the phone locked persists both the finish intent and enough session data to reconstruct review after process death; it must never silently mark the run saved.
4. With workout write-back off, Watch heart rate collection leaves no saved Apple Health workout. With write-back on, the Watch session and later iPhone export produce only one workout and one activity-ring contribution. Test the actual Watch session/builder behavior before choosing the export path.
5. Choose and document the minimum iOS/watchOS versions for the transport. This implementation retains iOS 15.4 and targets watchOS 9 with WatchConnectivity; verify that pair on devices while retaining ordinary phone running on older supported iPhones.
6. The current iOS project and TestFlight workflow can build, sign, verify, and install an app with a watchOS companion target and its additional bundle ID/profile. Verify the signatures and provisioning of the embedded Watch app/extension as well as `com.tropos.app`. The project uses Swift Package Manager; do not copy Podfile instructions from the older Live Activity runbook into this work.

If this gate fails, do not ship a Watch control that appears to work while disconnected. Record the failure and narrow the first release to the parts that pass paired-device testing. The gate is a technical test, not a claim about how Runna or Hevy implement their products.

### Current release gates

`VITE_CONNECTED_TRAINING_ENABLED` defaults off and the native iOS Release target sets `WATCH_RUN_RELEASE_ENABLED=NO`. The settings controls and native transport therefore remain unavailable in an ordinary release build. The Health export worker now reserves a server receipt before writing; the run deletion trigger leaves a tombstone that the exporting iPhone pages through for native cleanup. The PR macOS simulator compile passed. The manual TestFlight workflow can select a connected training pilot build that turns on both gates for that archive and verifies both signed app bundles. Use that private pilot for the paired iPhone/Watch acceptance matrix, including locked-phone commands, heart-rate capture without an implicit Health workout, a read-denied reinstall attempt, and a run deleted on another device. Start with workout export off; enable it only on a test account for the export, reinstall and deletion cases. Keep the ordinary release gate off until signing and device checks pass.

## Delivery sequence

1. **Paired-device proof and native packaging.** Add a small watchOS/WatchConnectivity or workout-mirroring prototype; exercise locked-phone state, disconnection, acknowledgements, and CI signing before expanding the React surface. Choose the final Watch bundle ID and signing arrangement here.
2. **Connection and permissions.** Extend Settings → Apple Health without changing the steps path. Add the Watch install/readiness states, separate heart rate and workout-write choices, and truthful web unavailable state. Update `Info.plist` text and privacy documentation before requesting or writing additional HealthKit types; the pre-implementation copy said Tropos only read steps and never wrote to Health.
3. **Run companion.** Mirror the existing active phone run to the Watch, add acknowledged controls and heart rate transport, and preserve phone-only Start and Finish paths. Keep the phone's offline queue and plan claim rules.
4. **Summary and Apple Health export.** Add timestamp-aware heart rate summaries with coverage, then opt-in, idempotent `HKWorkout` write-back and edit/delete reconciliation. The installed `capacitor-health` plugin has no workout writer or live heart rate stream, so this needs a native bridge rather than another call to the steps bridge.
5. **Release check.** Run the repo verification gate, native build/signing checks, and the paired-device matrix below. Release only after the first iOS build and real-device run path are working; a web deployment cannot deliver the Watch target.

### Later releases

- **Phone-free Watch run.** Watch owns GPS, timer, pauses, and a durable offline recording. Transfer retains a stable origin ID, original start/finish instants, start-local date and time zone. The phone applies the same route privacy and validity review before one canonical save. Before that release, change claim reconciliation so a late run cannot satisfy a newly changed plan unintentionally; today's claim map recomputes against the current schedule. Historical reads must also find late saves by event day. This is a separate specification and release gate.
- **Watch lifting.** Show the current exercise and rest timer, then add set entry only after the phone and Watch share stable exercise/set instance identities and layout revisions. Today's set logs are positional and the workout can be reordered during a session; a stale Watch index must never record a set against a different exercise. The phone remains the save authority until a separate offline-lifting contract exists.
- **Other health data and widgets.** Body weight, sleep, active energy, Home Screen widgets, and the Live Activity extension have their own decisions. They are outside this first release. In particular, Apple Health energy does not enter the calorie budget.

## Acceptance matrix

| Scenario                                                                             | Expected result                                                                                                                                                                                       |
| ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Planned outdoor run, connected Watch, phone locked                                   | Watch state and heart rate update; acknowledged Pause/Resume match the phone; the existing summary saves one run and grants one eligible plan claim.                                                  |
| Free run or run on a rest day                                                        | Watch mirrors the active run; completion receives only the plan credit the existing date, distance, and quality claim map grants.                                                                     |
| No Watch, Watch app absent, or no heart rate samples                                 | Phone start, GPS, pause, and save still work. The UI describes unavailable data without a zero or a false permission verdict.                                                                         |
| Watch disconnects during recording                                                   | The phone continues. Watch data becomes visibly stale and controls cannot claim success; reconnect restores authoritative phone state without replaying old commands.                                 |
| Double tap, delayed acknowledgement, or repeated Finish                              | One phone transition and one saved run. A late command for an ended session is rejected.                                                                                                              |
| Phone backgrounded or locked                                                         | The native feasibility gate proves controls and heart rate delivery at the promised cadence on a real paired device.                                                                                  |
| Offline phone save with privacy zones already confirmed, app restart, then reconnect | One retained run ID survives the queue. The Watch shows **Saved on iPhone · syncing** until server confirmation; HealthKit exports at most once after that confirmation.                              |
| Review or offline sync after a time-zone change                                      | The saved run stays on its original start-local date; the HealthKit workout uses the actual recording start/end and active duration rather than GPS waiting, pauses, or later save time.              |
| Privacy zone, route discard, or invalid GPS                                          | The existing summary protects the route or declines valid plan credit. No unreviewed route is sent to the Watch or Apple Health.                                                                      |
| Sign out, account switch, or Watch reinstall                                         | Old account/session data is cleared. No command, heart rate, or plan context crosses accounts.                                                                                                        |
| HealthKit write disabled, revoked, retried, edited, or deleted                       | No write without opt-in. Retries do not duplicate a workout. When access is revoked, corrections or deletion remain visibly pending until access returns and the old app-owned sample can be removed. |
| Web and iPhone without a Watch                                                       | Existing running works, and the connection page states availability accurately.                                                                                                                       |

Track aggregate connection attempts, successful paired runs, heart rate coverage, command timeouts, save outcomes, and duplicate prevention. Review real-device failures and support reports before extending the Watch to phone-free recording or lifting. Do not infer retention or subscription impact from the Mobbin captures.
