How to read this audit

Every finding below carries four labels at the top so AI agents and engineers cannot confuse a verified bug with a product opinion:

Priority — P0 production-blocking · P1 high-value next · P2 polish
Verification status — verified / partially verified / needs exact log / product recommendation / not yet investigated
Confidence — high (direct code evidence) / medium (code suggests risk, behaviour needs test) / low (hypothesis)
Fix type — security · data integrity · cost control · UX trust · accessibility · DevOps · documentation
Hard rule: a finding is not actionable until it has Evidence, Root cause, Risk, Recommended fix, Acceptance criteria, Verification command, and Suggested PR. Anything not labelled remains a hypothesis.

1. AI quota / rate-limit fails open and is non-atomic

Evidence
functions/index.js:164-196 — checkMonthlyQuota: reads scanUsage/{uid}, computes count + 1, writes the new count, and the catch block ends with the literal comment // fail open and returns { allowed: true, remaining: 999, limit: 999 }.
Root cause
Quota is treated as ordinary app state. It is actually a billing-control boundary: a paid-AI cap. Read-then-write across two RTTs has a race window, and any Firestore error grants unlimited paid calls.
Risk
  • Concurrent analyzeFood / analyzeFoodText calls can exceed the monthly limit.
  • Transient Firestore errors (network, rules) silently grant unlimited Vertex AI calls.
  • Cost spike + abuse vector. The Gemini kill switch is not consulted before quota is consumed.
Recommended fix
  • Wrap quota update in db.runTransaction with a server-side FieldValue.increment(1) guarded by a max-count read inside the same transaction.
  • Change catch behaviour from fail-open to fail-closed for cost-sensitive paths: return { allowed: false, remaining: 0 } and surface a "temporary limit" error to the client. The current fail-open default is acceptable for free reads but not for paid AI invocations.
  • Consult the Gemini kill switch BEFORE incrementing quota — otherwise a disabled-Gemini failure path still consumes a user's monthly count.
  • Audit logger calls in analyzeFood / analyzeFoodText paths and ensure full Vertex response bodies are not persisted to Cloud Logging in production. Use logger.warn(summary) not logger.warn(response).
Acceptance
  • 20 concurrent analyzeFood requests for one free user cannot exceed the monthly limit (emulator test).
  • Forced Firestore write failure does NOT return allowed: true on paid paths.
  • Free / pro / trial tier limits each enforce correctly.
  • Month rollover resets the counter exactly once.
  • Gemini kill switch blocks both image and text analysis before quota is consumed.
  • No full Vertex response bodies in Cloud Logging from production.
Verify
cd functions && npm test -- quota
Plus an emulator-driven concurrency harness (new) at functions/__tests__/quota.concurrency.test.js.

2. Stripe webhook has no idempotency and no out-of-order guard

Evidence
functions/index.js:720-840 — stripeWebhook processes checkout.session.completed, customer.subscription.updated, and customer.subscription.deleted. No reference to a processedEvents / stripeEvents collection. No comparison of event.created against any stored timestamp. No allowlist check on session.metadata price.
Root cause
Payment events are treated like regular app events. They are financial entitlement events and must be idempotent, ordered defensively, and server-authoritative. Stripe retries every webhook on 5xx; a duplicate delivery today re-runs the same write.
Risk
  • Duplicate webhook delivery re-grants pro on a refunded subscription.
  • An out-of-order customer.subscription.deleted (delivered late after a renewal) downgrades an active user.
  • A future "lifetime" purchase can be silently downgraded by a stale monthly-subscription-cancelled event.
  • Client-supplied priceId on the checkout-session creator can attach an unintended price.
Recommended fix
  • Maintain a stripeEvents/{event.id} doc with status; reject re-deliveries.
  • Store the event's created timestamp on the user doc as subscriptionUpdatedAt; reject updates whose event.created is older.
  • Maintain a server-side price allowlist; reject unknown priceIds at createCheckoutSession time.
  • Reject subscription.deleted if the user's stored stripeSubscriptionId doesn't match (a different subscription was cancelled).
Acceptance
  • Replaying the same Stripe event.id twice updates the user exactly once.
  • An out-of-order subscription.deleted arriving after a fresh subscription.updated → active does NOT downgrade.
  • An unknown priceId passed by the client is rejected with a 400.
  • Tests cover: duplicate event, out-of-order delete, refund, unknown price, lifetime-vs-monthly transition.
Verify
cd functions && npm test -- stripeWebhook

3. Apple IAP webhook has solid signature verification but no idempotency / staleness check

Evidence
functions/appleIAP.js:215-263 — appleIAPWebhook calls verifyNotification + verifySignedTransaction (✓ good). But there is no dedup on payload.notificationUUID or tx.transactionId. applySubscriptionToUser at appleIAP.js:164-194 decides isActive from tx.expiresDate > new Date() — it does NOT compare against the currently-stored subscriptionExpiresAt on the user doc.
Root cause
App Store Server Notifications V2 can deliver out-of-order. Without a stored high-water mark, a late EXPIRED notification arriving AFTER a fresh DID_RENEW will set subscriptionTier: "free" because the stale transaction's expiresDate is now in the past — even though the user has already renewed for another year.
Risk
  • Out-of-order Apple notifications can silently downgrade an active paying user.
  • Duplicate notification delivery (Apple retries on 5xx) runs the same write twice.
  • No record of which notifications have been processed makes incident response harder.
Recommended fix
  • Maintain appleNotifications/{notificationUUID} dedup doc; reject re-delivery.
  • Before writing subscriptionTier, compare the incoming transaction's expiresDate against the user's stored subscriptionExpiresAt. Only downgrade if the incoming is authoritative AND the user has no later transaction.
  • For lifetime / non-subscription products, store productId and NEVER let a subscription-event downgrade a lifetime entitlement.
Acceptance
  • Same notificationUUID delivered twice updates user exactly once.
  • Late EXPIRED after fresh DID_RENEW does NOT downgrade.
  • Lifetime entitlement survives a stale subscription-cancelled event.
  • Tests cover: duplicate notification, out-of-order expired, restore-of-other-user-transaction, refund.
Verify
cd functions && npm test -- appleIAP
Follow-up PR

4. Workout set completion fires PR detection on unvalidated input

Evidence
src/components/WorkoutSession.tsx:391-426 — completeSet():
  1. marks setLogs[ex][set].completed = true
  2. calls checkSetPR(exName, set.weight, set.reps, prMap, sessionCounts, 3)
  3. mutates prMap[exName][bucket] = { weight, reps, date }
  4. fires confetti and toast.success
All synchronous, no validation, no jump-size guard, no confirmation step. The undo path (lines 428-431) only tracks lastCompleted by indices; it does NOT revert the prMap mutation.
Root cause
The app treats workout set input as trusted once typed. But it directly affects long-term history (PR map persisted to profile, fed into Pro-tier insights, rendered on History & ExerciseHistory) and user trust. There is no central validator between user typing and PR persistence.
Risk
  • A fat-fingered 200kg × 5 bench becomes a permanent PR with confetti.
  • Negative weights / decimal reps / empty values can silently become valid "completed" sets.
  • Undoing the set leaves the false PR in prMap.
  • Downstream surfaces (fastest-effort challenges, Pro insights) consume the false PR.
Recommended fix
Central validator in src/lib/setValidation.ts: 
type SetValidationResult =
  | { ok: true; normalized: { reps: number; weight: number } }
  | { ok: false; severity: "block"; message: string }
  | { ok: false; severity: "warn"; message: string; confirmLabel: string };
Rules:
  • Reps: integer, finite, ≥ 0, ≤ sensible cap (e.g. 100).
  • Weight: finite, ≥ 0, ≤ sensible cap (e.g. 500kg / 1100lb).
  • Empty / NaN: { ok: false, severity: "block" }.
  • Huge jump (> 25% over current PR for the bucket): severity: "warn" with confirm step before PR detection runs.
  • Decimal reps: blocked.
  • Decimal weight: normalised to 0.5kg / 1.25kg step depending on exercise.
  • Bodyweight exercises (no weight input column): allow 0 weight, validate reps only.
Wire completeSet through the validator BEFORE the PR-detection block. On the undo path, also revert prMap and pop the corresponding entry from firedPRs.
Acceptance
  • Reps < 0 / decimal / empty cannot complete a set.
  • Weight < 0 / NaN cannot complete a set.
  • A weight jump > 25% over current PR requires explicit confirmation before confetti + toast.
  • Undoing a PR-set reverts both setLogs AND prMap AND firedPRs.
  • Bodyweight exercises validate reps without requiring a weight value.
  • Unit tests cover: negative reps, decimal reps, empty input, huge weight, huge jump, bodyweight movement, false-PR prevention.
Verify
npx vitest run src/lib/__tests__/setValidation.test.ts

PR E — Workout set validation + PR safety.

5. Playwright E2E suite blocked — exact failure captured

Evidence
e2e/responsive.spec.ts:71 — test.use({ ...devices['iPhone 14'] }) inside test.describe('Responsive — Safari standalone (PWA-ish)', ...). Live npx playwright test --list output: 
Cannot use({ defaultBrowserType }) in a describe group,
because it forces a new worker.
Make it top-level in the test file or put in the configuration file.

  at responsive.spec.ts:71

> 71 |   test.use({ ...devices['iPhone 14'] });
Nuance
Playwright DOES support test.use() inside test.describe() for most options. BUT devices['iPhone 14'] spreads a config object that includes defaultBrowserType: "webkit", and the defaultBrowserType property is one of the options that forces a new worker — which Playwright rejects inside describe. The Codex audit's diagnosis was directionally correct; the general "test.use inside describe is supported" rebuttal applies to most options but not to device configs.
Root cause
The responsive test duplicates the mobile project config that's already defined in playwright.config.ts:21-23. The test should run under that project, not declare its own device.
Recommended fix
  • Delete the test.use({ ...devices['iPhone 14'] }) line entirely.
  • Either: assign the responsive test to the mobile project via Playwright project filtering (npx playwright test --project=mobile), OR move the test to a file with no describe wrapper so test.use() sits at top level.
  • Audit ALL E2E specs for weak assertions (expect(count).toBeGreaterThanOrEqual(0)) — Sprint 8 already rewrote accessibility.spec.ts; the others may still carry the pattern.
Acceptance
  • npx playwright test --list succeeds with no parse errors.
  • npm run test:e2e passes from a clean checkout.
  • Responsive mobile test asserts real UI outcomes (not just root element existence).
  • Authenticated E2E surface coverage exists for Food / Run / Program / Settings / Upgrade (via seeded auth fixture) — flagged as follow-up.
Verify
npx playwright test --list  # config validation
npm run test:e2e            # full run

Evidence

  • Web still obtains a reCAPTCHA v3 token.
  • Debug-token flow documented in README for local dev.
  • Enforcement plan in README: client ships unenforced → verify token traffic for 1 week → enable enforcement on Functions → wait 1 week → enable enforcement on Firestore / Storage. Rollback path documented.

7. updateProfile swallows errors — settings UI cannot revert

Evidence
src/lib/auth.tsx:520-580 — updateProfile returns Promise<void>. Catch block logs + toasts but throws nothing and returns nothing. Callers cannot tell whether the persistence succeeded.
Risk
Settings controls optimistically update local state, then look "saved" to the user even when the Firestore write failed. Dark mode persists in localStorage regardless of Firestore success. Custom calorie targets can be silently overwritten by reactive TDEE recalculation.
Recommended fix
Change the contract: 
type UpdateProfileResult =
  | { ok: true }
  | { ok: false; error: unknown };

updateProfile(data, { throwOnError?: boolean }): Promise<UpdateProfileResult>
Default to result-returning; opt-in throwing for callers that prefer try/catch. Settings sections then revert optimistic UI on { ok: false }.
Acceptance
  • updateProfile returns { ok } or throws on demand.
  • Optimistic settings controls revert visibly on failure.
  • Dark mode does not persist in localStorage if the Firestore write fails.
  • Reactive TDEE recalculation preserves customCalorieTarget.
  • Tests cover failed update, successful update, dark-mode failure, custom-target preservation.
