LLM Council Report

Tropos Home Page — Improvements & Weaknesses
Question Counciled

What are the highest-impact improvements and weaknesses to fix on the Tropos home page — considering both UX (visual hierarchy, information architecture) and code quality (performance, maintainability)?

Council Verdict

Where the Council Agrees

Home is overloaded — 11+ widgets showing everything to everyone every time
Skeleton bug is urgent — Health Score loading failure erodes trust daily
Silent .catch() is unacceptable — you can't debug what you can't see
Dead imports (HybridBalanceCard, InsightStrip) must be removed
StackedCTACards.tsx at 18KB is a maintainability liability
Fix before redesign — stabilize the codebase before rethinking architecture

Where the Council Clashes

Fix vs. Rethink — Executor/Outsider say fix broken stuff first; Contrarian/First Principles say the information architecture is fundamentally wrong
Scope of change — Executor wants 4 days of cleanup; First Principles wants a complete reconception with user state machine

Resolution: Executor and Outsider are right on sequencing. Contrarian is right on direction. You cannot redesign a page you haven't stabilized, but stabilization isn't the endpoint.

Blind Spots the Council Caught

  • Unbatched Firestore queries are the root cause of the skeleton bug. Multiple independent reads fire sequentially, creating a network waterfall. Promise.all isn't just cleanup — it's the fix.
  • Zero test coverage on Home.tsx and StackedCTACards.tsx. Refactoring an 18KB component without tests is how you ship regressions.
  • The disabled ESLint rule is a broken quality gate. It signals linting is optional and lets dead imports and silent catches accumulate.
  • Firebase billing exposure. Unbatched queries multiply read costs. This is a money problem, not just performance.

The Recommendation

Phase 1 — Week 1: Stop the Bleeding
  • Fix Health Score skeleton by batching Firestore queries with Promise.all in a single useHomeData hook
  • Replace every silent .catch(() => {}) with actual error handling
  • Delete dead imports (HybridBalanceCard, InsightStrip)
  • Remove or fix the disabled ESLint rule
  • Fix weight decimal validation and hardcoded 0.4 protein multiplier
Phase 2 — Week 2: Structural Cleanup
  • Write integration tests for home screen data flow
  • Extract StackedCTACards.tsx into individual card components (pure extraction)
  • Measure LCP and bundle impact; set a performance budget
Phase 3 — Week 3+: Earn the Right to Redesign
  • Explore context-aware composition with data (what gets tapped, scroll depth, time-of-day)
  • Wire existing engines (performanceEngine, nutritionInsights, plateauDetection) to the home surface
  • Consider shipping HybridBalanceCard and InsightStrip if they add value

The One Thing to Do First

Create a useHomeData hook that batches all Firestore queries into a single Promise.all, returns a unified loading/error/data state, and replaces the 11 independent useState calls. This one change fixes the skeleton bug, eliminates the network waterfall, reduces re-renders, cuts Firebase read costs, and creates the single state object that makes every subsequent refactor possible.

The Contrarian

The fatal flaw everyone will dance around: this home page is a junk drawer. No amount of refactoring StackedCTACards.tsx or batching Firestore queries fixes the core problem — you're showing everything to everyone every time, and that's a product architecture failure, not a code one.

The skeleton loading bug is worse than it looks. A Health Score card that intermittently shows gray bars means your data-fetching has a race condition or an unhandled state. Users see this on the primary surface they open daily. This isn't a polish item — it's eroding trust in your most prominent metric.

Silent .catch(() => {}) is a ticking time bomb. You're swallowing errors on a page with 11+ useState calls and unbatched Firestore queries. When something breaks in production, you'll have zero signal.

The hardcoded 0.4 protein multiplier undermines "adaptive" — your literal brand promise.

The highest-impact improvement isn't code — it's cutting content. Pick the 3-4 things that matter for today's context and hide everything else behind a tap. Stop adding. Start subtracting.

The First Principles Thinker

The real problem isn't "what should we fix on the home page." It's: why does the home page try to be everything at once?

A fitness app home screen has one job: get the user into their next action within 3 seconds. Everything else is vanity metrics. Strip it down. Rebuild from the user's actual state machine:

User opens app. They're in exactly one of: pre-workout, mid-day tracking, or post-workout. The home page should detect which state and surface ONE primary CTA, not a buffet of cards competing for attention.

Health Score, Water, Weight, Steps, Energy breakdown, macro rings — these are all retrospective data. They belong on a dashboard tab, not the landing surface. The home screen is a launchpad, not a report.

The 18KB StackedCTACards monolith and 11 useState calls are symptoms, not causes. The cause is that nobody defined what the home page ISN'T.

You're asking "how do we improve this page" when the answer is "this page shouldn't exist in its current form."

The Expansionist

The massive unlock here is the home screen becoming a genuine adaptive coaching surface, not just a dashboard of cards.

The real opportunity: contextual home screen composition. If it's 7am and they have a lift scheduled, the Lift CTA should dominate. If they just finished a run, flip to recovery: protein nudge, hydration push, stretch suggestion. The infrastructure is already there — performanceEngine, phaseNutrition, plateauDetection, nutritionInsights — it's just not wired to the home screen.

Second unlock: collapse the scroll. Health Score + Water + Weight + Steps could be a single swipeable row. You cut scroll depth by 40% and increase engagement.

Third: the two dead imports (HybridBalanceCard, InsightStrip) are the biggest signal. Someone started building exactly this adaptive surface and stopped. Ship them.

Fourth: streak celebration on every extension, not just milestones. Tiny dopamine hits compound. The confetti infrastructure exists. Use it.

The code cleanup matters, but the upside is a home screen that feels like it thinks. That's what separates a fitness logger from a fitness coach.

The Outsider

The single biggest problem is that this home screen is trying to be a dashboard, a launcher, and a status page simultaneously. No one asked "what does the user actually need when they open this app?"

The loading skeleton issue is the real emergency. If your primary card sometimes shows gray bars instead of content, users see a broken app. Everything else is secondary.

11 useState calls means nobody knows what state the page is in. Silent .catch is lying to users. Two imported-but-never-rendered components tell me this codebase has dead code that nobody notices.

The 18KB single file is the maintainability killer. Not because of the size itself, but because every change to any card risks breaking every other card.

Priority: 1) Fix the skeleton/loading bug, 2) Delete dead imports (5 minutes), 3) Split StackedCTACards, 4) Replace silent catches, 5) Consolidate state. Skip the IA redesign for now. Fix what is broken and messy first.

The Executor

Here's what you do Monday morning, in order:

Day 1: Fix the Health Score skeleton bug — data race, add proper fallback. Two hours max.

Day 2: Clean up Home.tsx state management. 11 useState calls → single useHomeData hook. Batch Firestore queries with Promise.all. Kill silent .catch() calls. Remove dead imports. Remove disabled ESLint rule. Half-day refactor.

Day 3: Break up StackedCTACards.tsx. 18KB → 5 individual files. No logic changes, pure extraction. Unblocks future work without merge conflicts.

Day 4: Fix small logic bugs. Weight input decimal validation (regex). Hardcoded 0.4 protein multiplier (pull from profile). Streak animation (change threshold condition). 15-30 minutes each.

What I'd skip entirely: redesigning the information architecture, rethinking vertical scroll length, or restructuring action pill placement. Those are design discussions that'll burn a week. The current layout works. Users scroll — it's a phone. Four days, no design review needed.

All 5 reviewers ranked the Executor or Outsider as strongest. All 5 identified the First Principles Thinker as having the biggest blind spot — proposing a complete reconception while bugs ship daily.
